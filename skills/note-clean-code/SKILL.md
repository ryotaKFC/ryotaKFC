## 外部品質と内部品質
- 外部品質: ユーザーに見える部分
- 内部品質: 保守性・可読性・一貫性などユーザーには見えない部分。大体こちらが犠牲になりがち
- 内部品質を下げると割れ窓理論的に低品質なコードが積み重なる
  - 機能追加時に既存の(品質の低い)パターンに合わせてしまい、悪循環になる
  - 「いつか直す」はだいたい直されない
- 時間をかける = 良いコードができる、ではない。良いコードを書くには知識と経験が必要

## 技術的負債
負債は縦軸・横軸の2軸で整理できる
- 横軸: 技術知識の問題 / ドメイン知識の問題
  - 技術知識: 言語やフレームワークに起因する問題
  - ドメイン知識: 対象領域の知識(例: 出前サービスなら店舗・配達員に関する知識)
- 縦軸: 意図的な負債 / 変化による負債 / 学びによる負債

### 意図的負債
- 速度優先にした際に発生
- 良い書き方やドメイン知識を知っていながら、それを無視した書き方をすると発生する
- 避けられる負債なので、品質を下げるのではなくスコープを削るかリリース日を見直すべき

### 変化による負債
- 技術や仕様の変化によって既存のコードが古くなることで発生
- 銀行の利息のように、放置すると影響範囲が膨れ上がる
- 発生したら早期に回収すべき

### 学びによる負債
- 勉強で新しい知見やより良いドメイン表現を学ぶことで、現実と理想の間に乖離が生じて発生
- それ自体はポジティブな話だが、変化による負債と同様に早期回収が望ましい

## モジュールの凝集度(強度)
凝集度が高い(=機能的)ほど良い設計とされる。低い順から:

- **偶発的**: とりあえず動くだけのコード。絶対に避けるべき
- **論理的凝集**: フラグを渡すと動作が変わるモジュール。共通化のつもりでやりがちだが保守性が低く避けるべき
- **時間的**: 時間的に近いタイミングで動くものをまとめたもの(例: 初期化処理、UIフォアグラウンド時の処理)
- **手続き的**: 順番に実行する必要があるものをまとめたもの(例: ファイル操作)
- **通信的**: 同じデータを扱うモジュール群(例: 一つの引数を複数の関数に渡すような関数群)
- **逐次的**: ある処理の出力が次の処理の入力になるものをまとめたもの(例: パース後のデータを扱う処理)
- **機能的**: 単一の定義されたタスクを実現するモジュール。最も理想的(例: 「2点間の距離を計算する」モジュール)
