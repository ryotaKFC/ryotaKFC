# 外部と内部品質

外部品質：ユーザーに見える部分

内部品質：保守性とか可読性とか一貫性とかユーザに見えないところ。大体こっちが犠牲になる

# 品質を下げると

割れ窓理論的に品質の低いコードが積み重なっていく

例えば機能を追加するときに既存のパターンに合わせようと結果的に品質の悪いコードに合わせられてしまう

しかもいつか直そうはどうせ直さない

# 時間を書ける＝いいコードではない

質のいいコードは時間をかけて考えたとしても生まれない

結局必要なのは知識と経験

# 技術負債

縦軸と横軸が存在

横軸：技術知識の問題、ドメイン知識の問題

縦軸：意図的な負債、変化による負債、学びによる負債

!image.png

技術知識は言語とかフレームワークとかで発生する問題

ドメインはプログラミング対象の知識。

出前サービスなら店や配達員に関する知識が必要

### 意図的負債

大体速度優先にした時に発生する負債

良いコードを知ってるのに違う書き方をしたりドメイン知識を無視した挙動だけを合わせた書き方をすると意図的負債となる

これらは避けられる負債。品質を下げるよりターゲットを削る or リリース日を見直すべき

### 変化による負債

技術へんかなどで今まで使ってた技術が古くなったりドメイン知識の仕様が変更されると発生する

銀行の利息みたいに放置すると影響範囲が膨れ上がる

発生したらすぐ回収するべき

### 学びによる負債

勉強によって新しい知見を得たり、より良いドメイン表現を学んだりすると発生

これによって、現実と理想で乖離が生じ始めて負債となる

これは別にポジティブな話ではある。

けど変化による負債と同じく早期に回収が望ましい

# 凝縮度、結合度

---

### 偶発的

- とりあえず動く系のコード
- 絶対に避けるべき

### 論理的凝集

- フラグを渡すと動作変わるよ系モジュール
- 共通化の名目でやってしまいがちだけど普通に保守性が低いから避けるべき

### 時間的

- 時間的に近くに動作するものを集めたもの？
- 初期化だとか、UIフォアグラウンド時の処理とか

### 手続き的

- 順番に実行する必要があるものを集めたもの
- ファイル操作あたりとか

### 通信的

同じデータを扱う系のモジュール

一つの引数を複数の関数に渡す系の関数とか

### 逐次的

ある部分の出力が次の入力となるようなものを集めたモジュール

例えばParse後のデータを扱うものとか

### 機能的

単一の定義されたタスクを実現するモジュール

これが一番理想

例えば”2点間の距離を計算する”モジュールとか
